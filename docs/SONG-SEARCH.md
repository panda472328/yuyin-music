# 歌名搜索与优先来源

此文描述 0.5.3 源码，尚未发布。歌名模式在 Bilibili 官方全站搜索之外，首屏同时查询优先 UP 主的公开视频。结果显示为一个连续列表，不显示分类标题或空分类占位；内部仍按“单曲 → 合集 → 其他”优先级排列。视频模式保留 Bilibili 官方排序，适合视频或播客，不查询优先来源。

## 默认 UP 主

名单位于 `src/shared/preferred-music-uploaders.json`，React、历史 Electron 服务与 Windows 宿主共用同份文件；Windows 将它作为只读资源嵌入。以公开 MID 匹配身份，不凭昵称中的“音乐”“无损”等文字判断。

公开页面采样只证明当时可见的投稿模式和账号身份，不能保证所有历史／未来投稿。没有检测实际音质；Hi-Res／无损／高音质是来源自述标签。主页的“合集和系列”是视频组织方式，不把其中每个单曲认定为合集。

修改名单时核对公开主页 MID、近期投稿、歌曲和版本特征，记录 `name`、`profileUrl`、`reason`。MID 必须为正的 JavaScript 安全整数；原生端使用 `long`。最多查询配置中前四个合法、不重复的 MID，增加来源需考虑请求数量。改名单后重建 Windows 宿主，安装目录外没有可直接加载的配置文件。

## 召回和降级

- 主请求使用官方视频搜索 `keyword`、`order=totalrank` 和原页码，保留官方结果、总数与下一页状态。
- 歌名模式第一页额外使用官方 WBI 空间投稿搜索，原查询词、每 UP 第一页最多 10 条；两并发、共享六秒预算。显式 DJ／Remix 查询不额外查询这些来源。
- UP 返回的视频必须核对作者 MID，并逐视频判为相关非 DJ 单曲，才能与全站结果按区分大小写的 BVID 去重合并。重复项保留全站元数据。
- 可选请求超时、需要验证或格式异常时退回全站结果；主搜索失败仍显示错误，不能伪装为空列表。账号会话变化后拒绝晚到响应。不会自动触发登录、绕过验证或自动播放。
- 加载更多继续使用官方分页，不重复 UP 查询；对全部已加载结果重新合并、去重和排序，编号在连续列表中重新计算。网页预览仅处理全站结果，实际 UP 召回需 Windows 宿主。

## 内部分类与连续排序

标题先做 NFKC、大小写、空白和标点规范化，比较完整等值、前缀、包含、全部查询分词及逆包含关系。仅部分查询词相关（例如只匹配歌手而非所搜歌曲）进入“其他”，不会因优先 UP 主身份挤到单曲前列。UP 主和简介不充当歌手元数据。

普通查询中的 DJ／Remix／串烧、混音及加减速版本不作为优先单曲。查询明确指定 DJ／混音时保留版本意图。合集／歌单／专辑完整播放／多曲标题进入合集；教程、乐评、伴奏和无明确合集标签的二十分钟以上视频进入其他。规则基于标题和时长，不分析音频；误判结果仍保留供用户手动选择。

内部分类只决定连续列表中的优先级，不生成界面分组。单曲排在合集之前，合集排在其他之前；某一类没有结果时直接忽略，不显示标题或占位。优先名单中的相关非 DJ 单曲排在普通 UP 主的单曲之前，并跨 UP 主按有效播放量降序排列；缺失、非有限或负数播放量按 0 处理。播放量相同再按标题相关度、质量自述标签和原召回顺序稳定排序。普通 UP 主的单曲、合集和其他视频仍沿用原有标题相关度、质量标签与稳定顺序规则。

歌名搜索、联想、切换模式和加载更多都不会自动播放。点击任一结果后使用完整已加载列表作为播放队列；切换搜索模式保留输入框文本。视频模式不执行本地分类或重排，始终保持 Bilibili 官方顺序。

共享规则在 `src/shared/search-mode.ts`，原生对应为 `windows-host/BilibiliSearchRules.cs`，调整时同步两端和相关回归。验证入口为 `npm test`、`npm run test:host`；UI 需在 1440×950 与 1080×680 检查单个连续表格、无分类标题和空分类占位、连续编号、整体空状态、加载／错误、模式切换及跨页队列。
